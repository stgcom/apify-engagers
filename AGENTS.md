## Web Command Center (built 2026-08-07)
A static dashboard (`web/index.html` + `web/data.js`) generated from the
pipeline's latest artifacts, deployable to Surge.sh. No framework, no backend.

- **Generate:** `npm run web:generate` — reads `engagers-*.json`,
  `enriched-*.json`, `verified-*.json` (project root) and
  `output/leads-ready-*.csv`, `output/quarantined-*.csv`, then emits `web/`.
  Renders an "AWAITING FIRST RUN" state cleanly when no artifacts exist.
- **Deploy:** `npm run web:deploy` (or `web:deploy:ci`) — regenerates first,
  then `surge web/ --domain <sub>.surge.sh`. Requires `SURGE_LOGIN` +
  `SURGE_TOKEN` env vars; fails fast with instructions if missing. Default
  domain: `apify-engagers.surge.sh` (override with `SURGE_DOMAIN`).
- **Caveats:**
  - There is **no Surge MCP server** — deployment uses the official CLI via
    env token (the documented CI automation path). `findSurge()` falls back to
    `npx surge` if the global CLI isn't installed.
  - User must create a free Surge account and run `surge token` once to get
    `SURGE_LOGIN`/`SURGE_TOKEN`.
  - Surge CLI must be installed despite the npm quirk (`surge-setup.sh` was
    removed as bash-unusable on Windows; `npm i -g surge` or `npx surge`
    handles it, using the pack workaround if needed).
- **Data sources for the dashboard:** stage counts come from the JSON artifacts
  (root), lead/quarantine tables from the CSVs (`output/`). No secrets are
  ever embedded — only counts + non-sensitive lead fields.

## Apify API usage (per docs.apify.com/integrations, applied 2026-08-07)
- **Auth header only:** `runActor` now authenticates ONLY via
  `Authorization: Bearer <token>` — the token is no longer in the URL query
  (docs recommend the header; the URL param leaks the token into logs).
- **Exponential backoff + retry:** 429 (rate limit) and 5xx responses retry up
  to 3× with backoff + jitter (official client best practice).
- **Hard timeout:** AbortController caps each request (default 5 min) so a hung
  run can't stall the pipeline; aborts with a clear error.
- **Run options pass-through:** `runActor(actorId, input, { actor: { memory,
  build, timeout, waitForFinish } })`. Stage 1 passes `waitForFinish: 300` so
  sync runs don't wait forever.
- **Verified:** APIFY_TOKEN `apify_api_e9fz...` is valid (GET /v2/users/me → 200).
- **Security notes from docs:** prefer a scoped token (limit permissions to just
  the two actors + dataset read) for pipeline use; never put tokens in
  client-side code. Stage 1 run is now actually possible end-to-end with the
  tracked post URL + valid token.

## Profile Reactions Actor (added 2026-08-07)
- **Actor:** apimaestro/linkedin-profile-reactions, ID `FNhKFjeL8hWQtMeZI`.
  Harvests the posts a tracked profile has reacted to → expands the engager pool
  beyond just the tracked posts' own reactors/commenters.
- **Input:** `{ "usernames": ["satyanadella", "https://www.linkedin.com/in/..."] }`
  (slug OR full profile URL). Output rows carry `reactions[]`; each reaction has
  `author.{firstName,lastName,headline,profile_url}` + `post_stats` engagement counts.
- **Opt-in:** reads `tracked-profiles.txt` (new file, one slug/URL per line).
  Empty/missing file → pass is SKIPPED (paid actor, $5/1,000 — never runs
  without explicit profile entries).
- **Mapping:** `extractProfileReactionRow()` in `normalize.ts` flattens each
  reaction into an Engager: `author.profile_url` → profileUrl, first+last →
  name, `headline` → company, sum of totalReactionCount+comments+reposts →
  `engagement`. Source = `"profile_reactor"`.
- **Dedupe precedence:** reactor > commenter > profile_reactor (post-level
  engagers are a stronger intent signal). Engager CSV now includes `engagement`.
- **Log line:** `"N unique engagers extracted — X reactors, Y commenters,
  Z profile_reactors (deduped by profile URL from W raw)"`.

## GitHub Actions Trigger (added 2026-08-07)
The deployed command center can trigger the widening pass from the browser via
GitHub Actions — the secure relay (secrets live in GH, never in the static site).

- **Workflow:** `.github/workflows/extract.yml` — `workflow_dispatch` (manual
  "Run workflow" in the Actions tab) with an optional `profiles` input
  (comma-separated) appended to `tracked-profiles.txt`, then `npm run extract`.
  Secrets injected via `env:` from GH Actions secrets.
- **Required GH secrets:** `APIFY_TOKEN`, `EXA_API_KEY`, `GETLEADS_API_KEY`,
  `APOLLO_API_KEY`, `PROSPEO_API_KEY`, `MILLIONVERIFIER_API_KEY`. Only keys you
  set are used; missing ones fail that stage with a clear error.
- **Button:** "Run Extract ▸" in the command center hero links to
  `https://github.com/<owner>/<repo>/actions/workflows/extract.yml`. Set the
  `GH_REPO` env var when generating (`GH_REPO=grahamfirm/apify-engagers npm run
  web:generate`) to point it at the real repo (currently placeholder
  `your-org/apify-engagers`).
- **Setup needed (operator):** the project is NOT a git repo yet. To activate:
  1. `git init && git add -A && git commit` (`.gitignore` already excludes
     secrets + generated artifacts).
  2. Create a GitHub repo (e.g. `apify-engagers`), `git remote add origin
     <url> && git push -u origin main`.
  3. Add the secrets in GitHub → Settings → Secrets and variables → Actions.
  4. Set `GH_REPO` and regenerate + redeploy to point the button at the repo.
- **Cost/security:** manual `workflow_dispatch` only — a human always
  authorizes Apify spend; no public paid-trigger endpoint, no secrets in the
  site. Outputs uploaded as `engagers-output` artifact.
